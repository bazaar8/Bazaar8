2. CORE FINANCIAL & SYSTEM INVARIANTS TESTED
----------------------------------------------------------------------------------------------------
Every simulated scenario was verified against the following 13 non-negotiable invariants:

 [INV 1] Cash Conservation:
         cashBefore - cashAfter = allocatedShares * price.
         Net cash reduction must exactly equal the cost of allotted shares. Unallotted funds must 
         be refunded in full.

 [INV 2] Shares Integrity:
         holdingsQtyAfter - holdingsQtyBefore = allocatedLots * lotSize.
         No phantom shares or uncredited holdings allowed.

 [INV 3] Lot Size Consistency:
         allocatedShares % lotSize === 0 for every user.

 [INV 4] Maximum Allocation Cap:
         sum(allocatedLots across all users) <= totalLots.

 [INV 5] Undersubscribed IPO Guarantee:
         If demand <= totalLots, every applicant receives 100% of requested lots with 0 refund.

 [INV 6] Oversubscribed IPO Saturation:
         If demand > totalLots, sum(allocatedLots) === totalLots exactly (no unassigned lots).

 [INV 7] Per-Subscription Reconciliation:
         investedAmount = refundedAmount + (allocatedShares * price) for every subscription record.

 [INV 8] Per-User Reconciliation:
         sum(investedAmount) = sum(refundedAmount) + sum(allocatedShares * price) per user.

 [INV 9] System-Wide Conservation of Wealth:
         totalCash + totalHoldingsValue (at IPO price) before bidding === after allotment.
         Zero wealth creation or destruction across the entire user base.

 [INV 10] Numerical & Input Integrity:
          No negative balances, no NaN values, float precision kept to 2 decimal places, and float 
          lots (e.g. 1.5) strictly rejected.

 [INV 11] Weighted Average Holding Price:
          For users already holding the ticker prior to allotment, their new avgPrice must equal:
          ((existingQty * oldAvgPrice) + (newQty * ipoPrice)) / (existingQty + newQty).

 [INV 12] Single Holding Record per Ticker:
          No duplicate holding rows for the same ticker and positionType ("long").

 [INV 13] Subscription Status Consistency:
          Subscription status must accurately reflect result ('won' if allocatedLots > 0, else 'lost').

4. DEFECTS IDENTIFIED & FIXES IMPLEMENTED
----------------------------------------------------------------------------------------------------

DEFECT 1 [CRITICAL]: Holding Array Corruption on Pre-Existing Holders
  - Location: backend/engine.js (lines 166-196 in addLongHolding)
  - Bug: In the MongoDB aggregation pipeline ($map), document variables were referenced as "$h.*"
         instead of "$$h.*". In MongoDB expressions, "$h" evaluated to null, corrupting user holdings 
         into [null] and wiping out existing portfolios upon allotment.
  - Fix: Changed all references to "$$h.ticker", "$$h.positionType", "$$h.quantity", "$$h.avgPrice", 
         and "$$h".
  - Result: Pre-existing holdings now accurately compute weighted average price and increment quantity 
            without creating duplicate or null rows.

DEFECT 2 [HIGH]: Float Truncation & Share Mismatch in Subscription Validation
  - Location: backend/engine.js (lines 852-858 in subscribeIPO)
  - Bug: Using parseInt(data.requestedLots, 10) silently truncated floating-point bids (e.g. 1.5 lots 
         became 1 lot) instead of rejecting them. Also, client-provided requestedShares was not 
         validated against requestedLots * lotSize.
  - Fix: Implemented Number.isInteger(lots) check and enforced that requestedShares matches 
         lots * lotSize exactly, throwing validation errors on mismatched requests.
  - Result: Invalid bids are rejected immediately prior to balance deductions.

DEFECT 3 [CRITICAL]: Race Condition on High-Concurrency Subscriptions
  - Location: backend/engine.js (lines 868-915 in subscribeIPO)
  - Bug: Cash deduction and subscription array push were two non-transactional database updates. 
         If a client submitted 20 parallel requests, multiple cash deductions succeeded while only 
         one subscription was appended, causing unrefunded money deductions.
  - Fix: Implemented strict two-phase atomic compensation:
         1. Atomic cash deduction via User.updateOne({ uid, cashBalance: {$gte: cost} }, {$inc: -cost}).
         2. IPO subscription push via IPO.updateOne({ _id, "subscriptions.uid": {$ne: uid} }, {$push}).
         3. If the push fails (e.g. duplicate user or closed IPO), an automatic rollback immediately 
            refunds the cost with $inc: { cashBalance: +cost } and logs to console.error.
  - Result: 20 parallel requests from the same user result in exactly 1 successful subscription, 
            19 clean rollbacks, and zero unrefunded funds.

DEFECT 4 [HIGH]: MongoDB 16 MB Document Size Overflow Risk
  - Location: backend/engine.js (lines 586-590 & 696-702 in SystemState priceHistory sync)
  - Bug: The engine previously stored up to 7,200 history points per stock. With 50 stocks, the single 
         SystemState document grew to ~11 MB (dangerously close to MongoDB's 16 MB hard limit), 
         causing slow 15-second disk writes.
  - Fix: Capped history to 500 points per stock (approx. 42 minutes of 5-second tick history).
  - Result: SystemState document size dropped from ~11 MB to ~650 KB, reducing disk I/O by 94% and 
         ensuring fast, safe database writes.
